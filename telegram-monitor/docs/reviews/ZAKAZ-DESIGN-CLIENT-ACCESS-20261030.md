## Решение

Включение текущего клиентского адаптера для каналов пока не подготовлено к эксплуатации: в нём нет поддержки sponsored messages, предусмотренной §3.3 API Terms. Исключения для нашего фонового монитора в проверенных документах не найдено. Это основание не включать существующую реализацию, **не доказательство общей невозможности клиентского чтения публичных каналов**. Подписка сама по себе это условие не устраняет.

Для минимального подключения остаётся резервный маршрут **существующий Bot API после фактического добавления бота администратором**. Запрос подготовлен, но не отправлен. Клиентский маршрут оставлен отдельным условным тикетом TG-S16; глобальный запрет в коде не снят. Не предлагается обходить условия публичным HTML-поллером.

### Условия Telegram

- [API Terms](https://core.telegram.org/api/terms), проверены 30.10: §3.3 требует поддержку официальных sponsored messages у приложений, дающих доступ к содержимому каналов. В `reader.py`/`monitor.py` этой поддержки нет. §2.1 требует собственный api_id приложения. Рабочие настройки импортированы из пользовательского архива; принадлежность регистрации приложения отдельно не установлена.
- [Спецификация sponsored messages](https://core.telegram.org/api/sponsored-messages): предусмотрены получение, отображение и учёт фактических показов. Вызов получения с последующим отбрасыванием рекламы не был бы полноценной реализацией; фиктивные просмотры недопустимы. Отдельного освобождения фоновых мониторов здесь не установлено. Применимость требований к выбранному формату должна быть закрыта до включения, а не условным переключателем «всё разрешено».
- [Content Licensing](https://telegram.org/tos/content-licensing): публичность не даёт универсальную лицензию на произвольный сбор; использование должно укладываться в разрешённый сервис и условия правообладателя. Пакеты сообщений в LLM не передавались. Автоматический поток остаётся локальным и без LLM.
- [Типы каналов и супергрупп](https://core.telegram.org/api/channel) подтверждают различие `broadcast` и `megagroup`. [GetParticipant](https://core.telegram.org/method/channels.getParticipant) документирует `USER_NOT_PARTICIPANT`. [JoinChannel](https://core.telegram.org/method/channels.joinChannel) — отдельное действие пользователя, не часть выполненной проверки.

Утверждать, что Telegram запретил конкретному аккаунту читать zakaz_design, оснований нет. Утверждать, что достаточно удалить одну проверку и закончен допустимый клиентский адаптер, тоже нельзя.

## 2. Что потребовалось бы клиентскому адаптеру

Только после закрытия условий API и согласования подписки:

1. Явно разрешить одну пару `zakaz_design` / `-1001373050413`, без общего флага «читать все каналы». Остальные broadcast-каналы отклонять. Сохранить нынешнюю разрешённую супергруппу.
2. Проверять владельца сессии, точные username/peer ID, `broadcast`, собственное участие и ограничения. Смена ID, запрет сохранения/доступа или потеря участия останавливают новый источник; никаких автоматических join, повторных заявок или обхода.
3. Сохранить существующие `events.NewMessage(chats=entities)` и `MessageEdited`, `catch_up=False`, общий `extract` → `monitor.ingest`, прежние фильтр, SQLite, уникальность source/message и единственного получателя. Не добавлять `iter_messages`/массовую историю и отправку через аккаунт. Редакция старого поста, пришедшая новым update, не называется новой публикацией.
4. Указать точку включения в UTC/МСК. Старые публикации не выдавать за новые; редакции отслеживать по `edit_date`, сохранять первоначальное время публикации. Проверка дедупликации — только на изолированной БД с поддельным отправителем, с сохранением ручного статуса.
5. Выполнить необходимые требования к клиенту каналов; их отсутствие не маскировать новым allowlist или согласием только администратора. До этого расширение кода не объявлять реализованным.

**Выполняемый патч в рабочий `reader.py` не внесён:** условие допустимости текущего минимального варианта не выполнено. Приведённый объём — техническая спецификация TG-S16, не отчёт о готовом подключении и не результат live-тестов.

### Конкретные следующие действия

- Если возвращаемся к клиентскому варианту: сначала подтвердить соответствующий условиям формат работы с каналами и регистрацию API приложения; затем Максим вручную открывает канал под выбранным аккаунтом и нажимает «Подписаться» либо отдельно поручает это действие. **Сейчас подписываться только ради проверки не требуется:** это не закроет оставшиеся условия. Коды/пароли/API hash в чат не нужны.
- Для выбранного минимального резервного варианта: Максим передаёт [подготовленный запрос](../ZAKAZ-DESIGN-CONNECTION-REQUEST-20261030.md) администратору именно zakaz_design. Нужны согласованные условия чтения и фактическое добавление @uffweb_bot с минимальными правами получения публикаций, без права публикации/управления. Исполнитель никому запрос не отправлял. По [Bots FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get) бот получает публикации каналов, участником которых является. Вступление обычного аккаунта не даёт этих прав боту.
