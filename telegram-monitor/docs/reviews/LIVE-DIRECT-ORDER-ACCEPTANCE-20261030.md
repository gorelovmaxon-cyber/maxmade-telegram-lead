## Причина last_result

`2147946720 = 0x800710E0`; COM представляет то же значение как `-2147020576`. В Win32 это HRESULT с кодом **4320, ERROR_REQUEST_REFUSED**. Это не exit code работающего Python-процесса. [Официальное описание кода](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--4000-5999-).

У рабочей задачи установлен повторный триггер `PT1M` и `MultipleInstances=2 / IgnoreNew`. По [документации Microsoft](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-multipleinstancespolicy-settingstype-element) эта политика не запускает новый экземпляр, пока прежний работает.

Установление причины:

1. В рабочей задаче одна активная инстанция, процессы продолжают работу с прежнего времени, LastRunTime обновляется от `2026-10-30T14:27:28` до `2026-10-30T14:31:28`, а результат повторной попытки остаётся отказом. Это **повторяющийся результат минутных попыток**, не только старый утренний результат и не текущая поломка читателя/доставки.
2. Для проверки создана отдельная временная задача с тем же `IgnoreNew`, без Telegram, рабочей БД и импорта монитора. В 30.10.2026 14:26:27 МСК первый экземпляр работал с результатом **267009 / SCHED_S_TASK_RUNNING**. После второго триггера в 30.10.2026 14:26:36 МСК результат стал **-2147020576 / 0x800710E0**, а GUID и состояние Running остались прежними. **Отклонение нового запуска при работающем экземпляре воспроизведено с тем же кодом.**
3. Временная задача остановлена и удалена; проверено отсутствие её регистрации и процессов. Производственная задача и параметры журналирования не менялись.

Следовательно, текущая причина ненулевого результата согласована с конфигурацией и воспроизведена: **IgnoreNew отклоняет минутный запуск, потому что прежний экземпляр работает**. Исправлять работающий пилот или стирать этот результат перезапуском не требуется. Его нельзя трактовать как отказ обработки входящих событий.

Граница доказательства: Operational-журнал отключён; исходная запись конкретного отклонения рабочей задачи недоступна. Попытка отдельной ETW-трассировки получила Access denied из-за прав Windows, повышения прав и изменения глобального логирования не выполнялось. Поэтому есть прямое контролируемое воспроизведение и наблюдение рабочей конфигурации/экземпляра, но нет сохранённого Event 322 именно производственной попытки. Артефакт: `state/scheduler-ignore-new-probe-20261030.json`.
