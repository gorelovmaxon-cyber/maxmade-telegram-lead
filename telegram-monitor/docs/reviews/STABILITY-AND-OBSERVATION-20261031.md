## 2. Минимальная доработка диагностики

Добавлен `transport_diagnostics.py`; в `Telegram.call` подключены записи результата. Текущий backend urllib использует частный opener с тем же стандартным ProxyHandler; глобальные настройки и другие запросы не меняются. Фазы: setup, proxy_tcp/origin_tcp, proxy_connect, tls, http_request, http_headers, http_body. Записываются UTC, PID, имя API-метода из разрешённого списка, длительности, исход, числовые errno/winerror, HTTP/API-коды и retry_after. Значения исключений, URL, токен, текст сообщений, тело ответа, заголовки, chat_id, API hash и сессии не записываются.

Журнал `state/delivery-transport.jsonl`, ротация 2 МиБ + две резервные копии, до примерно 6 МиБ. Запись диагностики не должна ломать успешный запрос при ошибке файловой системы. Backend curl сохраняется; для него логируются общий результат/длительность/exit code, но разбиения TLS/CONNECT нет. В пилоте используется urllib. Диагностика сама не повторяет запросы, не посылает проверочные сообщения и не меняет состояние deliveries.

Семантика фильтра, send/uncertain, backoff, тайм-аутов и ручных статусов сохранена. Для HTTPException записывается метадата и исключение передаётся далее как прежде; обработка не превращена в новый автоматический retry. Предупреждение о неизвестном результате отправки не заменяется предположением об успехе.

Официальные описания поведения: [urllib Python 3.12](https://docs.python.org/3.12/library/urllib.request.html), [http.client](https://docs.python.org/3.12/library/http.client.html), [ssl](https://docs.python.org/3.12/library/ssl.html). TLS/HTTP-фазы получены инструментированием вызова стандартной библиотеки, а не разбором текста сообщений Telegram.

## 3. Отдельная причина остановки читателя — TG-S18

31.10 в **10:58:39 МСК** lifecycle зафиксировал AuthKeyUnregisteredError. В дальнейшем читатель многократно останавливался на проверке `is_user_authorized`; supervisor повторяет запуск с прежним пределом backoff 60 с. Это не чтение новых событий и не рабочий uptime. Число запусков не равно числу сетевых разрывов.

16:33:44 отдельная проверка GetState с receive_updates=False подтвердила AuthKeyUnregisteredError. По последующему указанию Максима проверен последний ZIP из «Загрузок»: **16:37:31** тот же ключ, такой же отказ. Архив не исполнялся, извлекались только ожидаемые SQLite/JSON в локальную временную область; проверка использовала авторизацию в памяти, без join/истории/получения updates. Рабочая сессия и .env не заменялись. Телефон/API hash/ключи не публиковались.

Это **недействительность серверной авторизации**, а не установленная блокировка аккаунта. Причина отзыва/сброса ключа неизвестна. Копирование того же файла не создаёт новую авторизацию: [Telegram связывает авторизацию с ключом](https://core.telegram.org/api/auth). Нужен новый локальный вход с доступом к коду или другой действительный аккаунт под контролем Максима. Запрошено только это недостающее условие; коды/пароли не запрашивались в чат. Нельзя обходить недоступность аккаунта использованием чужого доступа.

До восстановления авторизации оставлены работающими доставка и supervisor. Не утверждается, что весь пилот исправен или что можно принять новый заказ из потока. Существующий читатель не переключался на каналы/другие аккаунты/неодобренные группы.
