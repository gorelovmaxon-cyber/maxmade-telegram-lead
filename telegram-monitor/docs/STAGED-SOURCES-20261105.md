## Реализовано

- source_registry.py: отдельная локальная sources.sqlite3 — устойчивый peer, username/ссылка, тип, доступ и дата, правила, отдельные разрешения чтения/публикации и маршрут ответа, enabled, baseline/runtime, проверки и разрывы. 20 записей — **кандидаты**, не 20 подключений.
- multi_source.py: отдельные страницы/проверки/наблюдатели и ограниченные попытки восстановления для каждого включённого группового источника. Один владелец reader/delivery locks, одна callback/delivery-очередь. Сетевые вызовы доставки вынесены из цикла DOM; рабочая SQLite/классификатор прежние. Legacy pending не подмешиваются.
- Аккаунт проверяется по собственным Settings, источник — по точному публичному username и основному числовому avatar peer, членство — по действиям профиля. Typing/avatar участника в шапке не должен менять идентичность разговора. Проверки выполняются до и после чтения очереди.
- Каждый reconnect создаёт новый baseline. История/повторный показ/неизвестная редакция не превращаются в новое событие. Редакция принятого события сохраняет прежний ручной статус. Автор остаётся неизвестным, если DOM-контракт его не устанавливает.
- Намеренный Stop сохраняется. Контроллер восстанавливает host, но не перезапускает здоровые страницы при сбое одного источника. Текущие индивидуальные ошибки видны в source_states и реестре.
- resource_probe.py измеряет Working Set дерева собственного host, количество процессов и свободную физическую память, без командных строк/секретов. source_registry.py report формирует state/local-chrome/source-report.json.

Реестр умеет записывать тип channel, но новый runtime пока допускает только проверенные группы. Каналы не включать под видом групп. Многопользовательский сервис, биллинг, LLM и автоматические отклики не добавлены.
