### Управление текущим пилотом на Windows

Из этой папки:

```powershell
py -3 pilot.py status
py -3 pilot.py start
py -3 pilot.py stop
```

`start` устанавливает задачу `MaxMade-Telegram-Pilot`, если её нет, и включает запуск при входе пользователя. Планировщик запускает скрытый контролирующий процесс, тот — чтение и доставку. Повторный запуск не создаёт вторую пару. Завершившиеся рабочие процессы перезапускаются через 2–60 с; Планировщик проверяет запуск контролирующего процесса раз в минуту. Пароль Windows не сохраняется, используются обычные права текущего пользователя.

`stop` отключает задачу до следующего `start` и завершает только процессы проекта. Неизвестный результат прерванной отправки становится `uncertain` и требует ручной сверки. `status` отдельно показывает наличие процессов, свежесть состояния и успешную сетевую проверку за последние 90 с для текущего PID; у контролирующего процесса собственной проверки Telegram нет. Поле результата последней попытки запуска Планировщика не заменяет текущий статус процесса и сети: попытка запуска уже работающей задачи может быть отклонена.

Журналы: `state/lifecycle.jsonl` (старты, выходы и перезапуски), `state/*-health.json` (свежее состояние), `state/reader-pilot.*.log`, `state/monitor-pilot.*.log`, `state/supervisor.*.log`. Они не содержат тексты источников или секреты. На момент передачи пилот восстановлен. Сон/выход/выключение и отключённый прокси прерывают чтение; восстановление всех пропущенных событий не гарантировано. После изменения кода работающие процессы нужно перезапустить.

1. На этом ПК войти в отдельный аккаунт в официальном Telegram и самостоятельно вступить в группу, если правила позволяют чтение таким способом. Telegram Web не выдаёт эти параметры.
2. Открыть [Setup-client.cmd](Setup-client.cmd). В локальном окне мастер запросит API ID и API hash, сохранит их в `.env`, затем запросит номер выбранного аккаунта, код входа и при необходимости пароль 2FA. Секретный ввод скрыт и остаётся на ПК. Из чата никакие данные входа не запрашиваются. Для ручного запуска доступны `.venv\Scripts\python.exe reader.py configure` и затем `.venv\Scripts\python.exe reader.py login`. 3. После проверки правил добавить `MONITOR_CLIENT_SOURCES=top_ads_freelance` в `.env` и выполнить `.venv\Scripts\python.exe reader.py check`. При подтверждённом членстве команда напечатает отрицательный peer ID. Вписать его в `MONITOR_CLIENT_PEER_IDS` в `.env` и сверить, что это именно нужная группа.
4. Оставить один процесс `py -3 monitor.py run-live` для доставки и отдельно запустить `.venv\Scripts\python.exe reader.py run` для чтения. Первый реальный подходящий пост должен дать карточку с оригинальной ссылкой. Зафиксировать время публикации и отправки, затем перезапустить оба процесса и проверить отсутствие дубля.

Бот и клиентский адаптер используют одну SQLite. При остановленном ПК новые события клиентского адаптера не гарантированы: историческую выгрузку он намеренно не делает. Не запускать два экземпляра одного процесса. Постоянный сервер выбирается после пилота.

Сверить ID с аккаунтом Максима и вручную указать `MONITOR_OWNER_ID`. «Первый посетитель» не назначается автоматически.
3. Добавить бота в согласованную группу/канал, проверить права и privacy mode. Числовые отрицательные `chat_id` записать в `MONITOR_SOURCE_IDS` через запятую. Администратор и Максим подтверждают правила чтения/ответа.
4. Закрыть другой `getUpdates`/webhook потребитель того же бота. Из этой папки выполнить `py -3 monitor.py run-live`. Публичный веб-сервер не нужен. Контролируемый запрос проверить в чате Максима, затем записать результат в `docs/ACCEPTANCE.md`.

Неверная конфигурация выдаёт понятную ошибку; токен не печатается. Код не отвечает потенциальным клиентам. Личный ID владельца встроен в исходящие уведомления; входящие сообщения не меняют адресата. Callback требует ID владельца, того же приватного чата, ID отправленной карточки и подпись. `getChatMember` проверяет доступ к источнику при запуске и ежечасно. Состояние `ok` не доказывает, что privacy mode даёт весь поток; это проверяется контролируемым событием.

Источники: только явно перечисленные отрицательные `chat_id`. Новые сообщения и редакции получают Bot API через long polling. По документации Telegram ожидающие updates хранятся не дольше 24 часов; после более долгого простоя пропущенные события восстановить этим способом нельзя. Массовую загрузку старой истории код не делает. Удаление исходного поста может не прийти как событие. Для приватного источника ссылка не выдумывается. Подробный отбор — [connection-plan.md](docs/connection-plan.md).

## Надёжность и данные

Входные события уникальны по `(source_id, message_id)`; редакция обновляет текст без сброса ручного статуса. Одинаковый текст из разных источников остаётся отдельными карточками с пометкой похожести. Доставка хранится в SQLite. Ошибка 429 повторяется с задержкой; неверный токен/права останавливают доставку. Если результат `sendMessage` неизвестен из-за разрыва или HTTP 5xx, состояние `uncertain` требует ручной сверки в чате владельца и **не повторяется автоматически**. Это не абсолютная гарантия exactly-once. `status` покажет такие записи. После сверки оператор может вручную менять SQLite только после резервной копии; автоматического «переотправить всем» нет.

Тихие часы по Москве: 23:00–09:00; можно задать `MONITOR_QUIET_START/END`. Пока в это время все уведомления ждут. Сообщения старше `MONITOR_URGENT_HOURS=24` попадают в обычную очередь. Фрагменты и публичный контакт редактируются по истечении `MONITOR_RETENTION_DAYS=30`; `py -3 monitor.py prune` выполняет очистку вручную, live-сервис — ежечасно. Публикуемый текст карточки — до 700 символов без HTML-разметки. Журнал не выводит текст источников или токен. SQLite и `.env` хранятся локально; доступ к ним ограничить правами ОС.

Остановка текущего пилота: `py -3 pilot.py stop`; при прямом запуске в консоли — Ctrl+C. SQLite сохраняет состояние, прерванное `sending` после запуска требует сверки как `uncertain`. Для резервирования: `py -3 monitor.py backup`. Восстановление: остановить пилот, сохранить текущую БД отдельно и скопировать проверенную резервную `.sqlite3` в путь `MONITOR_DB`; после запуска проверить `status`. Схема версии 1 создаётся повторно безопасно при открытии. Миграций между версиями пока нет; перед изменением схемы нужен backup.

Текущий Windows-пилот уже использует задачу Планировщика, описанную выше; вторую задачу для тех же процессов не создавать. Постоянный сервер выбирается после пилота. На Linux потребуется запуск обоих компонентов в отдельных systemd-сервисах с одной рабочей папкой и SQLite, отдельным пользователем и локальным `.env`; текущий `pilot.py` предназначен для Windows. Развёртывание Linux пока не выполнялось.
